Why you should never put SOQL or DML inside a loop (Salesforce interview question)

This is one of the most common questions in a Salesforce developer interview. Most people answer "governor limits" and stop there. A strong answer explains what actually breaks, shows the fix, and shows how you would prove the fix works.

The question

"Why is it a bad practice to write a SOQL query or a DML statement inside a for loop?"

The short answer

Salesforce limits how much work one transaction can do. In normal (synchronous) code you get 100 SOQL queries and 150 DML statements. A trigger can receive up to 200 records at a time.

If your code runs one query per record, 200 records means 200 queries, and the whole transaction fails.

The error you will see

When the code goes over the limit, Salesforce stops it and rolls back everything it did. The error looks like this:

System.LimitException: Too many SOQL queries: 101

For DML inside a loop, the message is Too many DML statements: 151. A limit error cannot be caught with try and catch, so the only real fix is to change the code.

Code that breaks

This trigger copies an account's phone number to all of its contacts:

trigger AccountTrigger on Account (after update) {
    for (Account acc : Trigger.new) {
        List<Contact> contacts = [SELECT Id FROM Contact WHERE AccountId = :acc.Id];
        for (Contact c : contacts) {
            c.Phone = acc.Phone;
            update c;
        }
    }
}

It works when you test it with one account. It fails when a data load updates 200 accounts, because the query runs 200 times, and the update runs once for every single contact.

The fix

Run one query for all the accounts, change the contacts in memory, and save them all with one update. Trigger.newMap gives each account by its Id, so every contact can find its own account without another query.

trigger AccountTrigger on Account (after update) {
    List<Contact> contacts = [SELECT Id, AccountId FROM Contact WHERE AccountId IN :Trigger.newMap.keySet()];

    for (Contact c : contacts) {
        c.Phone = Trigger.newMap.get(c.AccountId).Phone;
    }

    update contacts;
}

Now the code uses one query and one DML statement, whether it receives 1 account or 200.

Other limits worth knowing

  • 200 SOQL queries in asynchronous code (Batch, Queueable, future methods), instead of 100
  • 50,000 records in total can be returned by all queries in one transaction
  • 10,000 records in total can be changed by DML in one transaction
  • 150 DML statements, in both synchronous and asynchronous code

How to prove your code is safe

Write a test that sends 200 records at once, the same as a real data load:

@isTest
private class AccountTriggerTest {
    @isTest
    static void updatesTwoHundredAccounts() {
        List<Account> accounts = new List<Account>();
        for (Integer i = 0; i < 200; i++) {
            accounts.add(new Account(Name = 'Test ' + i));
        }
        insert accounts;

        List<Contact> contacts = new List<Contact>();
        for (Account acc : accounts) {
            contacts.add(new Contact(LastName = 'Test', AccountId = acc.Id));
        }
        insert contacts;

        for (Account acc : accounts) {
            acc.Phone = '9999999999';
        }

        Test.startTest();
        update accounts;
        Test.stopTest();

        Assert.areEqual(200, [SELECT COUNT() FROM Contact WHERE Phone = '9999999999']);
    }
}

If the trigger had a query inside the loop, this test would fail with the limit error. You can also see how many queries your code has used at any point:

System.debug(Limits.getQueries() + ' of ' + Limits.getLimitQueries() + ' queries used');

What the interviewer wants to hear

  • You know the limits are per transaction, not per record.
  • You always write code for many records, not for one.
  • You know the pattern: collect the Ids, query once, change in memory, update once.
  • You test with 200 records to prove it.

Follow-up questions to expect

What if I need the related records for each parent?

Use a subquery, so one query brings each account together with its contacts:

List<Contact> contactsToUpdate = new List<Contact>();

for (Account acc : [SELECT Id, Phone, (SELECT Id FROM Contacts) FROM Account WHERE Id IN :Trigger.newMap.keySet()]) {
    for (Contact c : acc.Contacts) {
        c.Phone = acc.Phone;
        contactsToUpdate.add(c);
    }
}

update contactsToUpdate;

Or run one query and group the results in a Map<Id, List<Contact>>, with the account Id as the key.

Can I read the account's phone in the same query?

Yes. Query the contacts and include Account.Phone, the parent's field. Each contact then carries its account's phone, so you do not need a map at all:

List<Contact> contactsToUpdate = new List<Contact>();

for (Contact con : [SELECT Id, Phone, Account.Phone FROM Contact WHERE AccountId IN :Trigger.newMap.keySet()]) {
    con.Phone = con.Account.Phone;
    contactsToUpdate.add(con);
}

update contactsToUpdate;

This works in an after update trigger, because by then the query already sees the account's new phone number.

Can I avoid the limit by catching the error?

No. A LimitException cannot be caught. The code has to be written so it never reaches the limit.

Does the same rule apply to Flows?

Yes. A Get Records, Create Records or Update Records element inside a Flow loop counts against the same limits. Move it outside the loop: collect the records in a collection variable inside the loop, then save them with one element after it.
